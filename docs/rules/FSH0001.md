# FSH0001: Mutation point is not reachable from any test

|                        |            |
| ---------------------- | ---------- |
| **Rule ID**            | FSH0001    |
| **Category**           | FrameShift |
| **Default severity**   | Warning    |
| **Enabled by default** | Yes        |

## Cause

The production code contains a mutation point — a place where FrameShift can change the program —
inside a member that no discovered test reaches.

The reported message is:

```text
Mutation '{0}' at this location is not reachable from any test; a surviving mutant here would go unnoticed
```

`{0}` is the display name of the concrete mutation, for example:

```text
Mutation '> => >=' at this location is not reachable from any test; a surviving mutant here would go unnoticed
Mutation 'true => false' at this location is not reachable from any test; a surviving mutant here would go unnoticed
Mutation '0 => 1' at this location is not reachable from any test; a surviving mutant here would go unnoticed
```

## Rule description

> The analyzed member can be mutated, but no discovered test reaches it. A mutant introduced here
> would survive unnoticed, which means the behaviour is untested.

### What a mutation point is

A mutation point is a single syntax node that one of the mutation operators can replace by a
different node, so that the resulting program is still a valid C# program with different behaviour —
an arithmetic operator, a relational or equality operator, a logical or bitwise operator, a boolean,
nullable boolean, numeric or string literal, a negation, an increment or decrement, a compound
assignment, the two branches of a conditional expression, or a null-coalescing operator.

The string literal of a regular expression pattern is a mutation point several times over, because the
regular-expression pattern family rewrites the pattern *inside* it: every anchor, every quantifier,
every capturing group, every branch of an alternation, every character class and shorthand escape,
every lookaround assertion and every backreference is a point of its own. A pattern is recognised
where it is written as a literal in a `Regex` constructor or static call, in `[GeneratedRegex]` or in
`[RegularExpression]`, and only when the `RegexOptions` that apply to it can be resolved statically —
the options decide the grammar of the pattern, so a rewrite made under guessed options would not be the
mutation it claims to be. Because one pattern can easily carry dozens of such points, the family has a
switch of its own, `FrameShiftEnableRegexPatternMutations`, and it is consulted *before*
`FrameShiftMaxMutantsPerMember`, so switching the family off gives the budget of a member back to the
code around the pattern.

For every candidate the analyzer

1. recompiles the mutated syntax tree in memory and drops the candidate when the mutant does not
   compile (controlled by `FrameShiftVerifyMutantCompilation`, default `true`), because a mutant
   that does not build is not a mutation of the program at all,
2. classifies the candidate, and reports [FSH0002](FSH0002.md) instead when the mutant cannot
   change observable behaviour, and
3. reports FSH0001 only for the remaining, meaningful mutants — and only when the member enclosing
   the mutation point is not reachable.

At most `FrameShiftMaxMutantsPerMember` mutations (default `64`) are considered per member, so a
pathological member does not stall the build. Mutants beyond that budget are silently skipped.

### What reachability means here

Reachability is a purely static, compile-time property, computed in two passes because neither
compilation can see the whole picture:

- The **test side** analyzer walks the code reachable from every discovered test method inside the
  test assembly and records the documentation comment id of every member it touches that comes from
  outside the test compilation. A source generator serialises that into the test-surface manifest,
  and a packaged MSBuild target writes it next to the test project.
- The **production side** analyzer reads that manifest through `AdditionalFiles`, resolves the
  recorded ids against the current compilation to seed a reachable set, and then closes that set
  transitively over the production call graph: for every reachable member whose declaration lives in
  this compilation, every invocation, property, indexer, event, field or object creation its
  executable code resolves to becomes reachable in turn. Virtual and interface dispatch is
  approximated by adding the overrides and interface implementations declared in this compilation.

A member is reported only when neither it nor a member enclosing it is in that closed set. If the
manifest yields no reachable member at all, the analyzer reports [FSH0003](FSH0003.md) and stays
completely silent about mutation points, instead of blaming the code for a manifest problem. A
project with no manifest at all produces no FSH0001 either — the MSBuild warning
[FSH0005](FSH0005.md) reports the missing setup instead.

### False positives you will legitimately see

The closure is deliberately syntactic and side effect free — no test is ever executed. Four routes
into a member are therefore **not** followed, and a member that is genuinely covered only through
one of them is still reported:

- **Reflection.** A member invoked only through `Type.GetMethod`, `Activator` or an expression tree
  compiled at run time looks unreachable.
- **Dependency injection.** A registration that binds an abstraction to an implementation at run
  time is invisible. Only the syntactic implementation and override relationships described above
  bridge that gap.
- **Delegates stored in fields, properties or collections.** The delegate creation is recorded where
  it appears; the later invocation through the field is not connected to it.
- **Source-generated call sites.** Generated trees are part of the compilation and are walked like
  any other tree, but the generator is never run or reasoned about, and generated members that no
  source code references stay unreachable.

In addition, members without a declaring syntax in this compilation — most notably implicitly
declared default constructors — contribute no outgoing references, so field and property
initializers that only such a constructor would execute are not reached through it.

Every one of these limits errs on the side of reporting a gap a human can dismiss, instead of
silently claiming coverage that does not exist.

### The false negative in the other direction

Reachability is a yes/no property, and that is the rule's blind spot. FSH0001 asks whether *anything*
reaches the mutation point; it does not ask with how many inputs. A member reached by one test that
passes one pair of arguments is reachable, so FSH0001 stays silent — and a mutant that only changes
behaviour for some *other* input survives that single test unnoticed. Unlike the false positives
above, this is a false negative: a real gap reported as none, which is the dangerous direction.

[FSH0006](FSH0006.md) is the answer to exactly that case. Where FSH0001 is silent because the member
is reached, FSH0006 reports — as information — that everything reaching it contributes exactly one
input combination. The two rules are complementary and never fire for the same mutation point: FSH0001
covers "reached by nothing", FSH0006 covers "reached, but by a single case".

## How to fix violations

There are exactly two honest responses:

1. **Write a test that exercises the member.** Call the member from a test method — directly or
   through code the test calls — then rebuild the test project so the regenerated manifest records
   it, and rebuild the production project. The mutation point becomes reachable and the warning
   disappears.
2. **Accept the gap.** If the behaviour is genuinely not worth testing, suppress the diagnostic for
   that member or that file, as described below, and leave a reason in the suppression.

Do not "fix" the warning by deleting the mutation point unless the code was dead anyway.

## When to suppress warnings

Suppress FSH0001 when

- the member is genuinely covered, but only through reflection, dependency injection, a delegate
  stored in a field, or a source-generated call site — the closure cannot see those routes, so the
  report is a false positive; or
- the member is deliberately untested and you have decided to accept the gap.

Do not suppress it project-wide to make a build quiet. That turns the analysis off without
recording a decision.

In `.editorconfig`, for the whole project or for a path:

```ini
[*.cs]
dotnet_diagnostic.FSH0001.severity = none

# Only for generated adapters that are wired up through reflection.
[src/MyApp/Interop/*.cs]
dotnet_diagnostic.FSH0001.severity = none
```

On a single member, with the reason recorded:

```csharp
[SuppressMessage(
    "FrameShift",
    "FSH0001:Mutation point is not reachable from any test",
    Justification = "Invoked only through the plugin loader via reflection."
)]
public int Rank(int score) => score > 10 ? 1 : 0;
```

Around a single line:

```csharp
#pragma warning disable FSH0001 // Mutation point is not reachable from any test
        return score > 10;
#pragma warning restore FSH0001
```

To switch the whole analysis off for a project, set `FrameShiftEnabled` to `false` instead:

```xml
<PropertyGroup>
  <FrameShiftEnabled>false</FrameShiftEnabled>
</PropertyGroup>
```

## Example

Production code, `src/MyApp/Discount.cs`:

```csharp
namespace MyApp;

public sealed class Discount
{
    public decimal Apply(decimal amount) => amount > 100m ? amount * 0.9m : amount;

    public decimal ApplyStaffRate(decimal amount) => amount > 50m ? amount * 0.5m : amount;
}
```

Test code, `tests/MyApp.Tests/DiscountTests.cs`:

```csharp
namespace MyApp.Tests;

public sealed class DiscountTests
{
    [Test]
    public async Task Apply_AboveThreshold_AppliesTenPercent()
    {
        var actual = new Discount().Apply(200m);

        await Assert.That(actual).IsEqualTo(180m);
    }
}
```

The manifest the test project writes, `tests/MyApp.Tests/MyApp.Tests.frameshift-tests`:

```text
frameshift-test-surface/1
T M:MyApp.Tests.DiscountTests.Apply_AboveThreshold_AppliesTenPercent 1
R M:MyApp.Discount.#ctor
R M:MyApp.Discount.Apply(System.Decimal)
R T:MyApp.Discount
```

Each `T` line names a discovered test method and carries its test-case count — `1` here, because the
test takes no parameters and its inputs are hardcoded. The `R` lines that follow belong to it: they
are the members *that* test references. Reachability itself only needs the union of all `R` lines,
which is what this rule uses; the per-test grouping and the count exist for [FSH0006](FSH0006.md).

The real manifest also contains `R` lines for the members of every other referenced assembly the
test touches, including the test framework itself. Ids that do not resolve to a symbol of the
production compilation are simply ignored while the reachable set is seeded, so those extra lines
are harmless — they are shortened away here for readability.

`Apply` is seeded from the manifest and is reachable, so its mutation points are not reported.
`ApplyStaffRate` is in the same type but is never referenced from the test surface and is not called
by any reachable production member, so every meaningful mutant inside it is a gap. The diagnostic is
reported once per mutant, so the single line of `ApplyStaffRate` yields a whole group of warnings —
the relational operator is replaced by each of `<`, `<=` and `>=`, the multiplication by each of the
four remaining arithmetic operators, the two literals are negated, and the conditional expression
gets its branches swapped, its condition negated, and its condition forced to `true` and to `false`.
One of them:

```text
src/MyApp/Discount.cs(7,54): warning FSH0001: Mutation '> => >=' at this location is not reachable from any test; a surviving mutant here would go unnoticed
```

Adding a test for `ApplyStaffRate` and rebuilding the test project extends the manifest with

```text
T M:MyApp.Tests.DiscountTests.ApplyStaffRate_AboveThreshold_HalvesAmount 1
R M:MyApp.Discount.ApplyStaffRate(System.Decimal)
```

which makes the member reachable on the next production build, and the warning is gone. Because that
one test is the only one reaching `ApplyStaffRate` and contributes exactly one input combination, the
same build now reports [FSH0006](FSH0006.md) for the mutation points of that member — the gap is no
longer "untested", it is "tested with one input".
