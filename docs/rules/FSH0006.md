# FSH0006: Mutation point is reached by a single test case

|                        |            |
| ---------------------- | ---------- |
| **Rule ID**            | FSH0006    |
| **Category**           | FrameShift |
| **Default severity**   | Info       |
| **Enabled by default** | Yes        |

## Cause

The mutation point is reachable — some test does execute the member it sits in — but every test that
reaches that member contributes, all of them together, **exactly one input combination**. A mutation
that only matters for a *different* input would still leave every one of those tests green.

The reported message is:

```text
Mutation '{0}' is reached by a single test case, from test method '{1}'; a mutation that matters for other inputs would go unnoticed
```

`{0}` is the display name of the concrete mutation, `{1}` the documentation comment id of the single
test method that reaches the enclosing member:

```text
Mutation '>= => >' is reached by a single test case, from test method 'M:MyApp.Tests.PasswordPolicyTests.IsLongEnough_LongPassword_IsAccepted'; a mutation that matters for other inputs would go unnoticed
```

## Rule description

> The mutation point is reachable, but the tests reaching it exercise a single input combination. A
> mutant that changes behaviour only for other inputs would survive unnoticed.

FSH0001 answers a yes/no question: is this mutation point reached by *anything*? That question is
coarse. A method reached by one test that passes one pair of arguments is reported as covered, and for
mutation analysis that verdict is often wrong — the tests do run the mutated line, but they never run
it with the input at which the mutant differs from the original. FrameShift used to report such a
mutation point as covered and stay silent, which is a **false negative**: a real gap reported as
none, the dangerous direction.

FSH0006 closes that gap, one step short of the full answer.

### Why it is informational and not a warning

Deciding the question exactly would mean relating the argument values of every test to the mutated
expression and asking whether any of them makes the mutant observable. That is symbolic execution,
and it is out of scope for an analyzer that must finish inside a build.

What FSH0006 does instead is count input combinations, statically. A count of one is a strong hint
and nothing more: the analyzer cannot know whether that one combination happens to sit exactly where
the mutation matters. A single case at the boundary detects an off-by-one mutant perfectly well, and
FSH0006 reports it anyway. Because the rule is a heuristic that can be right about the count and
wrong about the consequence, it is reported as information — a prompt to look, not a build failure.

Note the direction: FSH0006 never claims coverage. It points at a place where coverage may be thinner
than [FSH0001](FSH0001.md)'s silence suggests.

### The counting rules

The number of cases is derived from the shape of the test method's declaration alone. Nothing is
executed: an analyzer must not run a data method to find out what it returns.

| Shape                                                                                    | Count                                             |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------- |
| A parameterless test method                                                              | exactly `1`                                       |
| `N` inline data attributes — `[Arguments]`, `[InlineData]`, `[TestCase]`, `[DataRow]`     | exactly `N`                                       |
| `[Matrix]` parameters whose value sets are literals                                      | exactly the size of the cross product             |
| A data source whose referenced member is a literal sequence                               | exactly the length of that sequence               |
| Any other data source — `[MethodDataSource]`, `[MemberData]`, `[TestCaseSource]`, `[DynamicData]`, `[ClassDataSource]` | **at least** `1`                                  |
| Inline data **and** a data source on the same method                                      | the sum, exact only when every part is exact      |

Three of these deserve a sentence.

**A parameterless test is one case, not an exempt case.** Its input values are hardcoded in its body,
which is exactly as narrow as a single `[Arguments]` row. Writing the values in the body instead of in
an attribute hides them from the reader; it does not widen what the test exercises. A parameterless
test is therefore counted, not skipped.

**An inline data attribute is applicable multiple times, and each usage is one case.** Three
`[Arguments]` on one method are three cases. The attribute is *not* a test marker in any framework
FrameShift supports: a method carrying `[Arguments]` without `[Test]` is not a test at all — TUnit
rejects it at compile time with `TUNIT0019` — so it contributes no cases and does not appear here. See
[FSH0004](FSH0004.md) for what does and does not make a method a test.

**A data source that cannot be enumerated statically yields a lower bound, never a count.** A
`[MethodDataSource]` means *at least one* case; the concrete number lives in the sequence the data
method returns, and the framework only learns it by **executing** that method during discovery. An
analyzer must not do that, so `1+` — "one or more" — is the honest static answer. It is a lower bound,
not "unknown".

### The trigger

For a given mutation point, FrameShift aggregates the counts of **all** test methods that reach the
mutation point's enclosing member, and reports FSH0006 only when

- the aggregated count is exactly `1`, **and**
- every count contributing to it is exact.

Both halves matter:

- A member reached by five tests has five input combinations and is never reported, however narrow
  each of those tests is individually.
- A single lower bound anywhere in the contributing set suppresses the finding entirely, even when it
  is a `1+`, because the true total could be far higher.

### Why a lower bound suppresses the finding

Because a lower bound is not a count. `1+` is compatible with one case and with ten thousand, and
FrameShift has no way to narrow it without executing code. Reporting on it would mean reporting on
every data-driven test in the solution — a `[MethodDataSource]` returning fifty rows would be
diagnosed exactly like a single hardcoded case. That noise would drown the finding that is worth
having, and the finding is only worth having when it is certain: exactly one combination, known
exactly.

The cost of that choice is a residual false negative. A `[MethodDataSource]` that really does return
one row is a single-case test and is not reported. That is the deliberate trade: silence on what the
analyzer cannot know, rather than a flood.

### How the manifest carries the counts

The aggregation needs to know *which test reached what*, which a flat union of referenced ids cannot
express. The test-surface manifest therefore groups its `R` lines under the preceding `T` line and
puts the case count on the `T` line itself:

```text
frameshift-test-surface/1
T M:MyApp.Tests.CalculatorTests.Add_Adds 3
R M:MyApp.Calculator.Add(System.Int32,System.Int32)~System.Int32
R T:MyApp.Calculator
T M:MyApp.Tests.CalculatorTests.Divide_Throws 1+
R M:MyApp.Calculator.Divide(System.Int32,System.Int32)~System.Int32
```

- The token after the test id is the case count: an exact integer (`3`) or a lower bound (`1+`).
- Every `R` line belongs to the closest `T` line above it. An `R` line that appears before any `T`
  line is malformed and is reported as [FSH0003](FSH0003.md).
- The header stays `frameshift-test-surface/1`. Nothing is released, so the format was replaced
  outright rather than versioned.

The full format is described in [FSH0003](FSH0003.md).

## How to fix violations

**Add a case — and put it where the mutation moves the boundary.** The point is not to make the count
exceed one; it is to exercise the input at which the mutant and the original disagree. The reported
mutation tells you where that is: `>= => >` moves a boundary by one, so the case to add is the
boundary value itself; `true => false` asks for an input that takes the other branch; a literal
mutation asks for an input on the other side of that literal.

Concretely, in order of preference:

1. **Add an `[Arguments]` / `[InlineData]` / `[TestCase]` / `[DataRow]` row at the boundary**, with
   the expected result spelled out. Cheapest change, and it is the one that actually kills the mutant.
2. **Add a second test method** for the neighbouring case, when the expected outcome differs in kind —
   a thrown exception, a different return shape — and does not fit the same parameter list.
3. **Widen an existing data source.** Do note that moving from inline rows to a `[MethodDataSource]`
   silences FSH0006 by turning the count into a lower bound, whether or not you added a case. Silence
   bought that way is not a fix.

Then rebuild the test project so the regenerated manifest records the new count, commit it, and
rebuild the production project. See [FSH0003](FSH0003.md).

## When to suppress warnings

Suppress FSH0006 when

- the single combination is deliberately the one that matters — it already sits at the boundary the
  mutation moves, and a second case would add nothing; or
- the member is genuinely exercised by more inputs than the analyzer can see, for example through a
  data source it counted as a lower bound in a *different* test that reaches the same member; or
- the mutation point is in a member whose behaviour does not depend on its inputs at all.

Because the rule is informational, the honest project-wide option is to switch it off rather than to
suppress it case by case, if the team decides it does not want the signal.

In `.editorconfig`, for the whole project or for a path:

```ini
[*.cs]
dotnet_diagnostic.FSH0006.severity = none

# Boundary cases are covered by the property-based suite, which FrameShift cannot count.
[src/MyApp/Numerics/*.cs]
dotnet_diagnostic.FSH0006.severity = none
```

Raising it is just as legitimate — a team that treats thin coverage as a defect can promote it:

```ini
[*.cs]
dotnet_diagnostic.FSH0006.severity = warning
```

On a single member, with the reason recorded:

```csharp
[SuppressMessage(
    "FrameShift",
    "FSH0006:Mutation point is reached by a single test case",
    Justification = "The single case is the boundary value; a second case would test nothing new."
)]
public bool IsLongEnough(string password) => password.Length >= 8;
```

Around a single line:

```csharp
#pragma warning disable FSH0006 // Mutation point is reached by a single test case
        return password.Length >= 8;
#pragma warning restore FSH0006
```

To switch the whole analysis off for a project, set `FrameShiftEnabled` to `false` instead:

```xml
<PropertyGroup>
  <FrameShiftEnabled>false</FrameShiftEnabled>
</PropertyGroup>
```

## Example

Production code, `src/MyApp/PasswordPolicy.cs`:

```csharp
namespace MyApp;

public sealed class PasswordPolicy
{
    public bool IsLongEnough(string password) => password.Length >= 8;
}
```

Test code, `tests/MyApp.Tests/PasswordPolicyTests.cs` — one test, one row:

```csharp
namespace MyApp.Tests;

public sealed class PasswordPolicyTests
{
    [Test]
    [Arguments("correct horse")]
    public async Task IsLongEnough_LongPassword_IsAccepted()
    {
        var actual = new PasswordPolicy().IsLongEnough("correct horse");

        await Assert.That(actual).IsTrue();
    }
}
```

The manifest the test project writes, `tests/MyApp.Tests/MyApp.Tests.frameshift-tests`:

```text
frameshift-test-surface/1
T M:MyApp.Tests.PasswordPolicyTests.IsLongEnough_LongPassword_IsAccepted 1
R M:MyApp.PasswordPolicy.#ctor
R M:MyApp.PasswordPolicy.IsLongEnough(System.String)~System.Boolean
R T:MyApp.PasswordPolicy
```

`IsLongEnough` is reachable, so [FSH0001](FSH0001.md) stays silent — and rightly so, the method is
executed. But the aggregated count for it is `1`, exact, so the production build reports:

```text
src/MyApp/PasswordPolicy.cs(5,63): info FSH0006: Mutation '>= => >' is reached by a single test case, from test method 'M:MyApp.Tests.PasswordPolicyTests.IsLongEnough_LongPassword_IsAccepted'; a mutation that matters for other inputs would go unnoticed
```

The diagnostic is exactly right here. `"correct horse"` is thirteen characters long, so `>= => >`
changes nothing for it: `13 >= 8` and `13 > 8` are both `true`, the test stays green, and the mutant
survives. The behaviour the method actually promises — that eight characters are enough and seven are
not — is untested.

Adding the boundary rows:

```csharp
    [Test]
    [Arguments("correct horse", true)]
    [Arguments("12345678", true)]
    [Arguments("1234567", false)]
    public async Task IsLongEnough_Password_MatchesMinimumLength(string password, bool expected)
    {
        var actual = new PasswordPolicy().IsLongEnough(password);

        await Assert.That(actual).IsEqualTo(expected);
    }
```

The regenerated manifest records three exact cases:

```text
T M:MyApp.Tests.PasswordPolicyTests.IsLongEnough_Password_MatchesMinimumLength 3
```

and the diagnostic is gone on the next production build — this time for a real reason: the
`"12345678"` row now fails under the `>= => >` mutant, so that mutant is genuinely killed.

The counter-example is worth keeping in mind. Replacing the three rows by

```csharp
    [Test]
    [MethodDataSource(nameof(Passwords))]
    public async Task IsLongEnough_Password_MatchesMinimumLength(string password, bool expected)
```

also removes the diagnostic, because the count becomes `1+` and a lower bound suppresses the finding —
regardless of whether `Passwords` returns three rows or one. FSH0006 is a heuristic on both sides: it
can point at a test that is fine, and it can miss a test that is not.
