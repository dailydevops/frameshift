# FSH0007: Mutation point is reachable without a behavioral assertion

|                        |            |
| ---------------------- | ---------- |
| **Rule ID**            | FSH0007    |
| **Category**           | FrameShift |
| **Default severity**   | Warning    |
| **Enabled by default** | Yes        |

## Cause

The mutation point is reachable — some test does execute the member it sits in — but the test surface
gives no credible basis for believing that a mutant here would ever be noticed: the member is either
only referenced as a bare method-group or delegate value, never actually called, or it is called but
no test that reaches it, directly or through code it calls, invokes a recognised, non-trivial
assertion afterwards.

The reported message is:

```text
Mutation '{0}' at this location is only reached by tests that carry no credible basis for believing a mutant here would be noticed; the reachable member is called, but no discovered test asserts on its behaviour
```

`{0}` is the display name of the concrete mutation:

```text
Mutation 'true => false' at this location is only reached by tests that carry no credible basis for believing a mutant here would be noticed; the reachable member is called, but no discovered test asserts on its behaviour
```

## Rule description

> The mutation point is reachable, but no discovered test both invokes the member and asserts on its
> behaviour afterwards. A mutant introduced here would survive unnoticed, even though [FSH0001](FSH0001.md)
> reports the member as covered.

FSH0001 answers a yes/no question: is this mutation point reached by *anything*? "Reached" there means
only that the test-surface manifest records the member's documentation comment id among the members a
test references — the reference can be a bare method-group conversion that is never invoked, such as

```csharp
Action<GeneratorInitializationContext> f = generator.Initialize;

await Assert.That(f).IsNotNull();
```

which reaches `Initialize` without ever calling it, or it can be an actual invocation whose result the
test never inspects at all. Either shape clears FSH0001 — the member is technically reached — while
proving nothing about what the member does. FSH0007 closes that gap: it is the analyzer's way of
saying *reached is not the same as verified*.

### How it differs from FSH0006

[FSH0006](FSH0006.md) and FSH0007 both refine what "covered" means once FSH0001 has already gone
silent, but along orthogonal axes:

- FSH0006 asks *how many* input combinations the reaching tests exercise, and reports when the answer
  is exactly one — coverage exists, but it is thin.
- FSH0007 asks whether the reaching tests establish *any* behavioral evidence at all — coverage may
  not mean anything was ever asserted on.

A mutation point could in principle fail both checks at once: reached by a single test that captures a
delegate and asserts only `IsNotNull()` on it. When that happens, `MutationCoverageAnalyzer.AnalyzeMutation`
reports FSH0007 and returns without ever reaching the FSH0006 check — behavioral reachability is tested
first, and FSH0006's single-test-case count is only computed and reported for mutation points that
already passed the behavioral check. FSH0007 therefore takes precedence: a mutation point is never
reported under both diagnostics, and being told "unverified" is strictly more urgent than being told
"thinly verified".

### The heuristic behind "non-trivial assertion"

Whether a test asserts on behaviour is decided the same way reachability itself is: by walking syntax,
never by executing code. A test method is walked, together with every member its own reachable code
calls, looking for an invocation whose simple method name is recognised as a non-trivial assertion.
The recognition is name-based, not type-based, because every mainstream .NET test framework and
assertion library spells the same handful of verbs differently, and matching a closed list of fully
qualified types would miss most of them.

A handful of recognised non-trivial names: `AreEqual`, `IsEqualTo`, `Throws`, `ThrowsAsync`, `Contains`,
`IsTrue`, `IsFalse`, `GreaterThan`, `ShouldBe`, `Verify`. A handful of names that count for reachability
but **not** as a non-trivial assertion on their own: `IsNotNull`, `NotNull`, `IsNull`, `Null`,
`NotDefault`, `IsDefault`. These trivial checks are excluded on purpose: a bare non-null check on a
captured delegate or reference is satisfied by any object regardless of what it does, so it asserts
nothing about the behaviour of the member the test claims to cover.

Being name-based, the heuristic is approximate by design, in the same generous direction the rest of
FrameShift's heuristics already accept: a production helper method that happens to be named `IsTrue`
is treated as a non-trivial assertion, which can produce a false negative — FSH0007 stays silent where
a stricter check might still fire. The opposite mistake, a genuinely well-tested member reported as
unverified because the assertion library spells its verb in a way the list does not recognise, is a
false positive and is the reason to suppress on a case-by-case basis rather than to distrust the rule
project-wide.

### The GeneratorDriver bridge is not a shortcut around this rule

[`GeneratorDriverBridge`](../../src/NetEvolve.FrameShift/TestSurface/GeneratorDriverBridge.cs) recognises
the well-known Roslyn test harness shape — `XxxGeneratorDriver.Create(generator).RunGenerators(...)` or
`.RunGeneratorsAndUpdateCompilation(...)`, optionally wrapping the generator in `.AsSourceGenerator()` —
and synthesizes a reachability edge straight to `IIncrementalGenerator.Initialize` or
`ISourceGenerator.Initialize`/`Execute`, because the driver invokes those methods from inside an
external assembly that the ordinary reachability walk can never see. That bridge answers "is it really
invoked, I promise" — it is a narrower, more precise stand-in for the call the walk missed.

It does not, on its own, answer whether the generator's *behaviour* was checked. A test that drives the
generator through `RunGenerators` and then asserts only `IsNotNull()` on the resulting driver, or on the
generated compilation, still reaches `Initialize` — now correctly, thanks to the bridge — but still
proves nothing about what the generator produced. FSH0007 applies to a bridged entry point exactly as
it applies to any other reachable member: a recognised, non-trivial assertion on the actual generated
output (the emitted sources, the diagnostics produced, the resulting compilation) is what clears it,
not the act of running the driver by itself.

### How the manifest carries the behavioral references

The test-surface manifest gains a second per-test line kind alongside `R`: a `B` line records that a
reference is not only reachable but also invoked and followed by a recognised, non-trivial assertion,
somewhere in the test method's own reachable code. Every `B` line is a subset of that block's `R` lines.

```text
frameshift-test-surface/1
T M:MyApp.Tests.GeneratorTests.Generate_EmitsExpectedSource 1
R M:MyApp.SourceGenerator.Initialize(Microsoft.CodeAnalysis.IncrementalGeneratorInitializationContext)
B M:MyApp.SourceGenerator.Initialize(Microsoft.CodeAnalysis.IncrementalGeneratorInitializationContext)
R T:MyApp.SourceGenerator
```

An older reader that does not know the `B` marker ignores the line, exactly as it ignores any other
unknown marker — a manifest carrying it stays readable by an older analyzer version, which simply falls
back to reachability-only precision for every mutation point in that member. The full format is
described in [FSH0003](FSH0003.md).

## How to fix violations

**Invoke the member and assert on what it actually did**, not on the fact that a reference to it
exists.

1. Replace a bare method-group/delegate capture with an actual call, at the point the test already
   holds enough context to check a result.
2. Assert with a recognised, non-trivial call against the *outcome* of that call — the returned value,
   a thrown exception, the observable side effect — not a null check on the delegate or the return
   value's mere presence.
3. For a source generator driven through `GeneratorDriver`, assert on the generated sources, the
   reported diagnostics, or the resulting compilation, not on the driver result being non-null.

Then rebuild the test project so the regenerated manifest records the new `B` line, and rebuild the
production project.

## When to suppress warnings

Suppress FSH0007 when

- the member is genuinely exercised only through an assertion library whose verb is not on the
  recognised name list, and you have confirmed by hand that the test does check behaviour; or
- the member's contract is exhausted by its identity — for example, a delegate is stored and compared
  by reference on purpose, and no further behaviour exists to assert on; or
- the team has decided, for a specific area, that reachability-only coverage is an acceptable trade.

Do not suppress it project-wide to silence a real gap. Because this diagnostic is a warning by
default, doing so is a visible, deliberate decision rather than a quiet one — which is the point.

In `.editorconfig`, for the whole project or for a path:

```ini
[*.cs]
dotnet_diagnostic.FSH0007.severity = none

# The recognised assertion names don't cover this project's custom assertion library.
[src/MyApp/Interop/*.cs]
dotnet_diagnostic.FSH0007.severity = none
```

On a single member, with the reason recorded:

```csharp
[SuppressMessage(
    "FrameShift",
    "FSH0007:Mutation point is reachable without a behavioral assertion",
    Justification = "Verified through MyApp.TestKit.AssertBehavior, which this analyzer does not recognise."
)]
public void Initialize(IncrementalGeneratorInitializationContext context) { /* ... */ }
```

Around a single line:

```csharp
#pragma warning disable FSH0007 // Mutation point is reachable without a behavioral assertion
        return password.Length >= 8;
#pragma warning restore FSH0007
```

To switch the whole analysis off for a project, set `FrameShiftEnabled` to `false` instead:

```xml
<PropertyGroup>
  <FrameShiftEnabled>false</FrameShiftEnabled>
</PropertyGroup>
```

## Example

Production code, `src/MyApp/Generators/GreetingGenerator.cs`:

```csharp
namespace MyApp.Generators;

using Microsoft.CodeAnalysis;

[Generator]
public sealed class GreetingGenerator : IIncrementalGenerator
{
    public void Initialize(IncrementalGeneratorInitializationContext context) =>
        context.RegisterPostInitializationOutput(ctx =>
            ctx.AddSource("Greeting.g.cs", "namespace MyApp; public static class Greeting { public const string Text = \"hi\"; }")
        );
}
```

Test code, `tests/MyApp.Tests/GreetingGeneratorTests.cs` — a bare delegate capture:

```csharp
namespace MyApp.Tests;

public sealed class GreetingGeneratorTests
{
    [Test]
    public async Task Initialize_IsNotNull()
    {
        var generator = new GreetingGenerator();
        Action<IncrementalGeneratorInitializationContext> f = generator.Initialize;

        await Assert.That(f).IsNotNull();
    }
}
```

`Initialize` is reachable — its documentation comment id appears among the manifest's `R` lines — so
[FSH0001](FSH0001.md) stays silent. But the reference is a method-group conversion that is never
invoked, and the only assertion in the test is `IsNotNull`, a trivial check. No `B` line is emitted for
`Initialize`, and the production build reports:

```text
src/MyApp/Generators/GreetingGenerator.cs(8,9): warning FSH0007: Mutation 'RegisterPostInitializationOutput removed' at this location is only reached by tests that carry no credible basis for believing a mutant here would be noticed; the reachable member is called, but no discovered test asserts on its behaviour
```

The diagnostic is exactly right: the test would pass unchanged if `Initialize` did nothing at all, or
emitted the wrong source, or emitted no source; `f` is non-null in every one of those cases.

Fixing it means driving the generator and asserting on what it produced:

```csharp
    [Test]
    public async Task Initialize_RegistersGreetingSource()
    {
        var driver = CSharpGeneratorDriver.Create(new GreetingGenerator().AsSourceGenerator());

        driver = (CSharpGeneratorDriver)driver.RunGenerators(CSharpCompilation.Create("Test"));
        var result = driver.GetRunResult();

        await Assert.That(result.GeneratedTrees).HasSingleItem();
        await Assert.That(result.GeneratedTrees[0].ToString()).Contains("Greeting");
    }
```

The `GeneratorDriver` bridge recognises the `CSharpGeneratorDriver.Create(...).RunGenerators(...)` shape
and connects the test straight to `GreetingGenerator.Initialize`. This time the test also reaches a
recognised, non-trivial assertion — `Contains` — on the actual generated output, so the regenerated
manifest records a `B` line for `Initialize` and the diagnostic is gone on the next production build:
a mutant that changes what `RegisterPostInitializationOutput` registers, or removes the call outright,
now makes `GeneratedTrees` empty or wrong, and the test fails.
