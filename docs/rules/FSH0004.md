# FSH0004: Test method does not reference any production member

|                        |            |
| ---------------------- | ---------- |
| **Rule ID**            | FSH0004    |
| **Category**           | FrameShift |
| **Default severity**   | Info       |
| **Enabled by default** | Yes        |

## Cause

A discovered test method, and everything it calls inside the test assembly, references no member of
any assembly outside the test compilation, so it contributes nothing to the test surface.

The reported message is:

```text
Test method '{0}' does not reference any production member
```

`{0}` is the minimally qualified display name of the test method, and the diagnostic is reported on
the method's name:

```text
Test method 'DiscountTests.Placeholder()' does not reference any production member
```

## Rule description

> The test method does not reference any member of the production assembly, so it cannot contribute
> to the tested surface.

The test-side analysis walks the code reachable from every discovered test method — method bodies,
expression bodies, constructor initializers and member initializers, transitively through the members
of the test assembly itself — and records every referenced member that comes from _outside_ the test
compilation. Methods, properties, fields, events and named types are recorded; attribute usages and
signatures are deliberately skipped, because they describe the test, not the code it exercises.

When that recording produces nothing at all for a test method, FSH0004 is reported for it. Such a
test cannot make a single mutation point reachable, so it can never influence
[FSH0001](FSH0001.md) in either direction.

The rule is reported per test framework **version**, because each version has its own analyzer and each
analyzer sees its own set of test methods. FrameShift ships five of them — TUnit, xUnit v2, xUnit v3,
NUnit and MSTest — and a project using several at once reports the tests of each version from the
analyzer that recognises them.

Detection is uniform across all five: a framework version is detected when its well-known test
attribute type resolves **or** when the compilation references one of that version's assemblies.
Either signal is enough. Because xUnit v2 and v3 both declare `Xunit.FactAttribute` — in `xunit.core`
and in `xunit.v3.core` respectively — each of the two adapters resolves that type inside its own
assembly, so a project referencing both versions is analysed by both, and each one recognises only the
attributes of the version it owns. Detection alone never produces a diagnostic, though: an analyzer
that finds no test method of its own framework version stays completely silent, so merely referencing a
framework package you write no tests for adds nothing to the build log.

### What exactly counts as a reference

"Outside the test compilation" means any other assembly, not only your production assembly. A test
that calls the assertion API of its test framework, or a type from the base class library, already
references members outside its own compilation and is therefore not reported — even though it
exercises no production code. FSH0004 answers "does this test reach outside its own assembly at
all".

The bar for reaching outside is low, and that is worth knowing before reading a report. A local
declared with `var` or with a predefined type keyword — `var total = 0;`, `int count = 0;` — binds
that keyword to a type of another assembly, and so does any operator that binds to one. All of them
count as a reference. What is left over, and what the rule therefore actually fires on, is a body
that is empty or that does nothing but evaluate literals and call members of the test assembly
itself.

### The legitimate cases

- **An intentionally empty placeholder** — a test that only records a pending scenario, or one whose
  body is deliberately commented out while a feature is being built.
- **A test that asserts on a fixture or on test infrastructure only**, and does so without leaving
  the test assembly — for example a test that verifies a test data builder or a theory-source method
  whose reachable code stays inside the tests.
- **A test that exercises the test framework itself**, such as a smoke test checking that the runner
  is wired up, when it does so without calling into the framework's own API.

In all of these the information is still worth having: it makes visible that this test does not
protect any production behaviour.

### The illegitimate case

A test that no longer tests anything. This is what the rule is actually for: after a refactoring the
production call was moved, inlined into a helper that was then deleted, or replaced by a value the
test now computes itself. The test still has a name that claims coverage, still passes, and protects
nothing. A name like `Calculate_WithNegativeInput_Throws` on a body that only manipulates a local
variable is the typical shape.

## How to fix violations

1. Read the test. If it is supposed to exercise production code, restore the call that was lost and
   assert on its result.
2. If the test genuinely protects nothing and the behaviour it claimed to cover is tested elsewhere,
   delete it. A test that asserts nothing about the system under test costs build time and creates
   false confidence.
3. If the test legitimately exercises only test-side code, keep it and suppress the diagnostic with a
   justification, so the next reader does not have to work it out again.

After changing a test, rebuild the test project so the regenerated manifest reflects the new surface,
and commit the manifest. See [FSH0003](FSH0003.md).

## When to suppress warnings

Suppress FSH0004 for the legitimate cases above: a test of a fixture or of test infrastructure, a
smoke test of the framework itself, or a deliberate placeholder. Prefer the narrow, per-method form,
because a project-wide suppression also hides the tests that really did stop testing something.

In `.editorconfig`, for a whole project or a path:

```ini
[*.cs]
dotnet_diagnostic.FSH0004.severity = none

# The builders in this folder are tested by themselves.
[tests/MyApp.Tests/Builders/*.cs]
dotnet_diagnostic.FSH0004.severity = none
```

On a single test method:

```csharp
[Test]
[SuppressMessage(
    "FrameShift",
    "FSH0004:Test method does not reference any production member",
    Justification = "Placeholder for the legacy import scenario, implemented in the next iteration."
)]
public void Pending_ImportOfLegacyFormat()
{
    // Intentionally empty.
}
```

Around a single test:

```csharp
#pragma warning disable FSH0004 // Test method does not reference any production member
    [Test]
    public void Builder_WithDefaults_UsesTestAssemblyStateOnly() => _builder.Reset();
#pragma warning restore FSH0004
```

## Example

```csharp
namespace MyApp.Tests;

public sealed class DiscountTests
{
    [Test]
    public async Task Apply_AboveThreshold_AppliesTenPercent()
    {
        var actual = new Discount().Apply(200m);

        await Assert.That(actual).IsEqualTo(180m);
    }

    [Test]
    public void Apply_BelowThreshold_KeepsAmount()
    {
        // The production call and the assertion were lost in a refactoring.
        Record(Expected());
    }

    private static decimal Expected() => 40m;

    private static void Record(decimal amount)
    {
    }
}
```

The first test references `MyApp.Discount` and its `Apply` method, so it contributes to the test
surface. The second one leaves the test assembly nowhere — `Record` and `Expected` are declared
right here, and a literal binds to nothing — while its name still claims that it covers the
below-threshold branch:

```text
tests/MyApp.Tests/DiscountTests.cs(14,17): info FSH0004: Test method 'DiscountTests.Apply_BelowThreshold_KeepsAmount()' does not reference any production member
```

Because that branch is now unprotected, the production build reports the corresponding gap as
[FSH0001](FSH0001.md) — the two diagnostics together tell the whole story. Restoring the body

```csharp
var actual = new Discount().Apply(40m);

await Assert.That(actual).IsEqualTo(40m);
```

removes both.
