# FSH0003: Test-surface manifest is missing or malformed

|                        |            |
| ---------------------- | ---------- |
| **Rule ID**            | FSH0003    |
| **Category**           | FrameShift |
| **Default severity**   | Warning    |
| **Enabled by default** | Yes        |

## Cause

A test-surface manifest reached the compiler, but it cannot be used: its content is not available,
it is not well formed, it records nothing usable for the compilation being analysed, or — on the
test side — it no longer describes the tests of the project it belongs to.

The reported message is:

```text
Test-surface manifest '{0}' could not be read: {1}
```

`{0}` is the full path of the manifest file, `{1}` is the concrete reason. The diagnostic is
anchored at the beginning of the manifest file itself, not at any source line.

## Rule description

> FrameShift needs a readable test-surface manifest to know which production members are covered by
> tests. Without it, reachability cannot be determined.

Both sides of the analysis report this rule:

- The **production side** (`MutationCoverageAnalyzer`) reports it for every
  `*.frameshift-tests` file among the `AdditionalFiles` that it cannot read or parse, and — when the
  reachable set ends up empty — for every file that parsed but contributed nothing.
- The **test side** reports it once per project for the manifest checked in next to the test
  project, when that manifest no longer matches the test surface the current compilation produces.
  There is one test-side analyzer per supported framework version — TUnit, xUnit v2, xUnit v3, NUnit
  and MSTest — and in a project that uses several of them at once only the first awake one performs
  the comparison, in that fixed order. The diagnostic therefore appears once, not once per framework
  version, and the surface it is compared against is the union of the surfaces of every awake version,
  so a project mixing frameworks — or mixing xUnit v2 and v3 — is never reported stale merely because
  one analyzer cannot see the other's tests.

A project with no manifest at all does **not** produce FSH0003. The analyzer stays silent, because
the project has not opted in; the MSBuild warning [FSH0005](FSH0005.md) reports the missing setup
instead. A test project that is about to write its very first manifest is likewise not reported.

### The manifest format

A manifest is a plain UTF-8 text file (no byte order mark) whose name ends with
`.frameshift-tests`. The default file written by the packaged MSBuild target is
`$(MSBuildProjectDirectory)\$(MSBuildProjectName).frameshift-tests`, configurable through
`FrameShiftTestSurfaceManifestFile`.

```text
frameshift-test-surface/1
T M:MyApp.Tests.DiscountTests.Apply_AboveThreshold_AppliesTenPercent
R M:MyApp.Discount.#ctor
R M:MyApp.Discount.Apply(System.Decimal)
R T:MyApp.Discount
```

The rules the parser applies:

| Element                     | Meaning                                                                                                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `frameshift-test-surface/1` | The mandatory header. It must be the first non-empty, non-comment line and must match exactly.                                                                            |
| `T <id>`                    | The documentation comment declaration id of a discovered test method.                                                                                                     |
| `R <id>`                    | The documentation comment declaration id of a production member referenced from the test surface.                                                                         |
| Blank lines                 | Ignored.                                                                                                                                                                  |
| Lines starting with `#`     | Ignored, so a manifest may carry comments.                                                                                                                                |
| Any other marker            | Ignored — both an unknown single-character marker and a first token that is longer than one character — so a future manifest version stays readable by an older analyzer. |

Every line is trimmed before it is inspected; the marker is separated from the id by white space. A
`T` or `R` line without an id is a parse error. Ids are compared ordinally and are not interpreted
by the reader — resolving them against a compilation happens later.

The canonical file the generator produces is the header line, then all `T` entries, then all `R`
entries, both groups sorted ordinally, one line feed per line and a trailing line feed. Ordering,
comments and other formatting never influence any comparison, because only the two id sets are
compared.

### The failure modes and what you actually see

**1. The content is not available.** The compiler handed the analyzer an additional file whose text
cannot be read.

```text
warning FSH0003: Test-surface manifest 'C:\src\MyApp\MyApp.Tests.frameshift-tests' could not be read: the content of the additional file is not available to the analyzer
```

On the test side the same situation reads `the content of the file is not available.`

**2. The file is malformed.** The parser stops at the first bad line and names it with a 1-based
line number:

```text
warning FSH0003: Test-surface manifest 'C:\src\MyApp\MyApp.Tests.frameshift-tests' could not be read: Line 1: expected the test-surface manifest header 'frameshift-test-surface/1', but found 'frameshift-test-surface/2'.
warning FSH0003: Test-surface manifest 'C:\src\MyApp\MyApp.Tests.frameshift-tests' could not be read: Line 4: the 'R' entry does not specify a documentation comment id.
warning FSH0003: Test-surface manifest 'C:\src\MyApp\MyApp.Tests.frameshift-tests' could not be read: The test-surface manifest does not contain the required header 'frameshift-test-surface/1'.
```

If the parser reports no detail at all, the fallback reason is used: `the file is not a well-formed
test-surface manifest` on the production side, `the file is not a well-formed test-surface
manifest.` on the test side.

**3. The manifest is empty or stale.** These are reported only when the manifest parsed cleanly but
still cannot drive the analysis. On the production side there are two variants, and both appear only
when the reachable set is empty — once per successfully parsed file:

```text
warning FSH0003: Test-surface manifest 'C:\src\MyApp\MyApp.Tests.frameshift-tests' could not be read: the manifest does not record a single referenced production member, so it is empty or stale; rebuild the test project to regenerate it
warning FSH0003: Test-surface manifest 'C:\src\MyApp\MyApp.Tests.frameshift-tests' could not be read: none of the production members recorded in the manifest exist in this compilation, so the manifest belongs to a different project or is stale; rebuild the test project to regenerate it
```

The second variant is the important one: a manifest whose recorded members no longer exist in the
compilation — after a rename, a move or a manifest copied from another project — is reported **here**
instead of producing a flood of [FSH0001](FSH0001.md) warnings for every mutation point of the whole
assembly. When the reachable set is empty the production analyzer names the real cause once and then
stays completely silent about mutation points.

On the test side, staleness is detected by comparing the id sets and is reported with the exact
difference:

```text
warning FSH0003: Test-surface manifest 'C:\src\MyApp\MyApp.Tests.frameshift-tests' could not be read: the recorded test surface no longer matches the tests of this project, so the manifest is stale and must be regenerated (3 id(s) added, 1 id(s) removed).
```

## How to fix violations

Rebuild the test project. The source generator recreates the manifest from the current test surface
and the packaged MSBuild target writes it to
`$(MSBuildProjectDirectory)\$(MSBuildProjectName).frameshift-tests`, overwriting it only when the
content actually changed. Then commit the file, so that the production build of every other machine
and of CI sees the same surface.

```console
dotnet build tests/MyApp.Tests/MyApp.Tests.csproj
git add tests/MyApp.Tests/MyApp.Tests.frameshift-tests
```

Then rebuild the production project so the analyzer picks the new file up.

Checklist for the individual causes:

- **Wrong or missing header, truncated file, hand-edited entries** — do not edit a manifest by hand.
  Delete it and rebuild the test project.
- **Merge conflict markers in the file** — resolve by regenerating, not by editing. The manifest is a
  generated artifact; either side's version is safe to discard.
- **`none of the production members … exist in this compilation`** — the manifest belongs to a
  different project, or the production code was renamed after the manifest was written. Verify that
  the file next to the test project is the one being handed to the production project, and rebuild
  the test project.
- **The manifest records nothing at all** — the test project produced no production reference. Check
  [FSH0004](FSH0004.md) for the individual tests, and verify that the test project actually
  references the production project.
- **A manifest is picked up twice**, for example a copy in an output directory: the default glob
  excludes `bin` and `obj`, `$(BaseOutputPath)` and `$(BaseIntermediateOutputPath)`. If you copy
  manifests elsewhere, exclude them yourself or set `FrameShiftEnableDefaultManifestItems` to
  `false` and add the files you want to `@(AdditionalFiles)` explicitly.

## When to suppress warnings

Suppress FSH0003 only when you deliberately keep a manifest that the analysis cannot use — for
instance a project that is being migrated and whose manifest is intentionally not regenerated yet.
Suppressing it otherwise hides the fact that reachability is being decided on stale data, which
makes every [FSH0001](FSH0001.md) verdict of that project untrustworthy.

Because the diagnostic is anchored at the manifest file and not at a source line, `.editorconfig` is
the mechanism that actually applies:

```ini
[*.cs]
dotnet_diagnostic.FSH0003.severity = none
```

The attribute and pragma forms exist for completeness and work only where a source location is
involved:

```csharp
[SuppressMessage(
    "FrameShift",
    "FSH0003:Test-surface manifest is missing or malformed",
    Justification = "The manifest is regenerated in a follow-up change."
)]
```

```csharp
#pragma warning disable FSH0003 // Test-surface manifest is missing or malformed
#pragma warning restore FSH0003
```

To stop the analysis from looking at manifests at all, disable FrameShift for the project:

```xml
<PropertyGroup>
  <FrameShiftEnabled>false</FrameShiftEnabled>
</PropertyGroup>
```

## Example

A manifest that was edited by hand and lost its header:

`tests/MyApp.Tests/MyApp.Tests.frameshift-tests`

```text
T M:MyApp.Tests.DiscountTests.Apply_AboveThreshold_AppliesTenPercent
R M:MyApp.Discount.Apply(System.Decimal)
```

The production build reports:

```text
MyApp.Tests.frameshift-tests(1,1): warning FSH0003: Test-surface manifest 'C:\src\MyApp\tests\MyApp.Tests\MyApp.Tests.frameshift-tests' could not be read: Line 1: expected the test-surface manifest header 'frameshift-test-surface/1', but found 'T M:MyApp.Tests.DiscountTests.Apply_AboveThreshold_AppliesTenPercent'.
```

No [FSH0001](FSH0001.md) is reported alongside it: without a usable manifest the analyzer refuses to
judge the production code at all. Rebuilding the test project restores the header and the two
entries, and the production build goes back to reporting real gaps.
