# FSH0002: Mutant cannot change observable behaviour

|                        |            |
| ---------------------- | ---------- |
| **Rule ID**            | FSH0002    |
| **Category**           | FrameShift |
| **Default severity**   | Info       |
| **Enabled by default** | Yes        |

## Cause

A candidate mutant compiles, but FrameShift can prove that it produces exactly the same observable
behaviour as the original code, so no test could ever distinguish the two.

The reported message is:

```text
Mutation '{0}' cannot change observable behaviour ({1})
```

`{0}` is the display name of the mutation, `{1}` is the precise reason the classifier proved. For
example:

```text
Mutation '2 => 3' cannot change observable behaviour (the mutation only changes a compile-time attribute argument)
Mutation '+ => -' cannot change observable behaviour (the mutated value is never consumed by its statement)
Mutation 'true => false' cannot change observable behaviour (the containing member does nothing but throw)
```

## Rule description

> The mutant is equivalent to the original code, so no test could ever distinguish it. Such mutants
> are reported for information only and do not indicate a testing gap.

This diagnostic is **not** a problem report. It is the opposite of [FSH0001](FSH0001.md): it tells
you that a mutation point exists but is not worth a test, because there is no test that could ever
fail on it. A mutation point classified this way is never reported as a gap — the classification
runs before the reachability verdict, so an equivalent mutant inside an unreachable member produces
FSH0002 and not FSH0001.

Use it to understand why a piece of code produces no coverage demand, and to decide that a member
which looks untested is in fact untestable at the mutation level.

### Every check the classifier implements

The checks run in this order, cheapest first, and the first one that proves triviality wins. Each
one produces exactly the reason string shown:

- **Identical rewrite** — the replacement node is syntactically the same code as the original, so
  the mutant is not a mutation at all.
  Reason: `the mutant is syntactically identical to the original code`
- **Constant folding** — both the original and the mutated expression have a provable compile-time
  constant value and those values are the same. Folding is done only where it is safe: `int` and
  `double` arithmetic (computed in `long` for `int`, so an overflowing result is rejected instead of
  folded wrongly), relational and equality operators, shifts with the language's shift-count masking,
  bitwise and logical operators over `bool` and `int`, and the unary operators. Division and modulo
  by zero are never folded, because they throw and are therefore observable. Positive and negative
  zero are told apart by their bit pattern; not-a-number operands are handled explicitly so that
  `==` semantics are not silently replaced by `Equals` semantics.
  Reason: `the mutated expression folds to the same constant`
- **Throw-only body** — the method, accessor, property, indexer or local function containing the
  mutation consists of nothing but a `throw` statement or a `throw` expression, so the member never
  produces a result a test could compare.
  Reason: `the containing member does nothing but throw`
- **Unreachable statement** — the compiler itself reports unreachable code (`CS0162`) covering the
  mutation location, so the mutated code never runs.
  Reason: `the mutated statement is already unreachable`
- **Discarded statement value** — the mutated subtree has no side effect (no invocation, assignment,
  object creation, `await`, increment or decrement), and the outermost expression that still carries
  the mutated value is the expression of an expression statement, so the value is computed and
  thrown away.
  Reason: `the mutated value is never consumed by its statement`
- **Discard assignment** — same as above, except that the value is the right-hand side of a simple
  assignment to a discard in a statement of its own, `_ = value;`.
  Reason: `the mutated value is assigned to a discard`
- **Attribute argument** — the mutation sits inside an attribute or an attribute argument, so it
  only changes metadata baked in at compile time.
  Reason: `the mutation only changes a compile-time attribute argument`
- **Default parameter value** — the mutation sits in the `= value` clause of a parameter.
  Reason: `the mutation only changes a default parameter value`
- **Case label** — the mutation sits in a `switch` label.
  Reason: `the mutation only changes a compile-time case label`
- **Constant declaration** — the mutation sits in a `const` local declaration, a `const` field
  declaration or an enum member declaration.
  Reason: `the mutation only changes a compile-time constant`
- **Well known infrastructure member** — the containing member is a method or property named
  `ToString`, `GetHashCode`, `Equals` or `Dispose`, whose mutants carry no information about the
  tested behaviour.
  Reason: `the containing member is a well known infrastructure member`
- **Compiler generated member** — the containing member is implicitly declared.
  Reason: `the containing member is compiler generated`
- **Excluded member** — the containing member, or any of its containing types, carries
  `[ExcludeFromCodeCoverage]` or `[GeneratedCode]`.
  Reason: `the containing member is excluded from coverage`
- **Obsolete member** — the containing member, or any of its containing types, carries `[Obsolete]`.
  Reason: `the containing member is marked obsolete`

Checks that need semantic information — constant folding, unreachable code, the discard assignment
and the symbol-based exclusions — are skipped when the mutated node does not belong to the syntax
tree of the semantic model being analysed. The discard assignment is the one exception: without a
usable model it still recognises a left-hand side spelled literally `_`.

### Why the classifier is deliberately conservative

The classification is one-sided on purpose. A mutant that is wrongly called _not_ trivial costs a
single diagnostic a reviewer can dismiss. A mutant that is wrongly called trivial silently hides a
real testing gap, which is exactly what FrameShift exists to find. Every check therefore reports
triviality only when it can actually prove it, and stays silent in every uncertain case: unsupported
constant types, foreign syntax trees, overflowing folds, division by zero, and every shape a check
does not fully understand. The cost of that direction is the occasional FSH0001 on code that could
not have been distinguished by a test anyway — never a missing warning.

## How to fix violations

Nothing needs fixing. FSH0002 is informational and reports a fact about the code, not a defect.

If the volume is not useful to you, turn the diagnostic off — either with the MSBuild property that
stops the analyzer from reporting these mutants at all:

```xml
<PropertyGroup>
  <FrameShiftReportTrivialMutants>false</FrameShiftReportTrivialMutants>
</PropertyGroup>
```

or with the usual analyzer configuration shown below. The MSBuild property is cheaper, because the
analyzer then never creates the diagnostic in the first place.

If the reason surprises you, the reason string names the check. A mutation reported as _never
consumed by its statement_ or _already unreachable_, for instance, often points at code that can be
deleted.

## When to suppress warnings

FSH0002 is `Info`, so it never breaks a build and never appears as a warning. Suppress it when the
information is simply not interesting for a project, a file or a member.

In `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.FSH0002.severity = none
```

On a single member:

```csharp
[SuppressMessage(
    "FrameShift",
    "FSH0002:Mutant cannot change observable behaviour",
    Justification = "The constant-only mutants of this options record are expected."
)]
public sealed record Options(int Retries = 3);
```

Around a single line:

```csharp
#pragma warning disable FSH0002 // Mutant cannot change observable behaviour
        const int Timeout = 30;
#pragma warning restore FSH0002
```

## Example

`src/MyApp/Retry.cs`:

```csharp
namespace MyApp;

using System;

public sealed class Retry
{
    private const int MaxAttempts = 2 + 1;

    public void Fire()
    {
        // The value of the addition is computed and thrown away.
        _ = MaxAttempts + 1;
    }

    public int Scale(int value) => throw new NotSupportedException("not scaled");
}
```

The build reports, among others, at `Info` severity:

```text
src/MyApp/Retry.cs(7,37): info FSH0002: Mutation '+ => -' cannot change observable behaviour (the mutation only changes a compile-time constant)
src/MyApp/Retry.cs(12,13): info FSH0002: Mutation '+ => -' cannot change observable behaviour (the mutated value is assigned to a discard)
src/MyApp/Retry.cs(15,68): info FSH0002: Mutation '"..." => ""' cannot change observable behaviour (the containing member does nothing but throw)
```

None of these three locations produces an FSH0001 gap, even though no test references `Retry` at
all: there is no test that could have detected the difference, so demanding one would be noise.

Note that the literal operators already refuse to mutate a literal in a position that requires a
compile-time constant — an attribute argument, a `const` initializer, a default parameter value, a
`case` label, a `goto case` statement or a constant pattern. The constant-only reasons above are
therefore produced by the operator-level mutations that remain possible in such a position, as with
the `2 + 1` initializer on line 7.
